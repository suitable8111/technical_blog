## 요약: AI 에이전트가 같은 작업을 두 번 실행해서 실제로 중복 결과물을 만든 사례가 발견됐습니다

최근 GeekNews에 올라온 질문 하나가 MCP(Model Context Protocol) 도구를 여러 개 연결해 에이전트를 운영하는 개발자들 사이에서 화제가 되고 있습니다. 핵심은 이겁니다.

> "같은 도구를 같은 인자로 두 번 호출하고, 결과까지 같은 경우"를 벤치마크 트레이스에서 세어봤더니, 실제로 문서나 스프레드시트가 중복 생성된 사례가 확인됐다는 것입니다.

## 숫자로 보는 중복 실행 현황

작성자가 공개 벤치마크 트레이스 6,780개를 분석한 결과는 다음과 같습니다.

- 전체 중복 실행 후보: **8,042건**
- 단순 반복(작업 완료 선언 등)을 제외하면: **4,249건**
- 그중 상태를 변경하는 도구(문서 생성, DB 쓰기 등)의 중복 호출: **3,432건**
- 응답에 담긴 엔티티 ID를 비교해 **실제로 두 개 이상 생성된 것으로 확인된 건: 159건**

예를 들면 같은 제목의 문서가 두 개, 같은 스프레드시트가 무려 네 개나 만들어지는 식입니다. 문제는 이런 중복이 **에러 없이** 조용히 일어난다는 점입니다. API 호출 두 번 모두 200 OK를 반환하고 로그도 깨끗해서, 사후에 로그만 봐서는 발견하기 어렵습니다.

## 왜 벤치마크만으로는 한계가 있을까

작성자도 이 점을 솔직하게 인정하고 있습니다. 이 데이터는 전부 22개 모델이 태스크를 푸는 **벤치마크 기록**이지, 실제 프로덕션 서비스 로그가 아닙니다. 게다가 공개 데이터셋 8개를 뒤졌지만 이 현상을 관측할 수 있는 건 단 하나뿐이었다고 합니다. 대부분의 벤치마크는 정답률 채점 목적으로 설계돼서, 중복이 발생하면 그냥 오답 처리되고 끝나버리는 구조이기 때문입니다.

또 흥미로운 점은, 도구(서버) 개수와 중복률 사이에 단순한 비례 관계가 없었다는 것입니다.

- 두 데이터셋 비교: 도구 20개 vs 523개인데 중복률은 0.80% vs 2.41%로 3배 차이
- 태스크당 서버 수로 나눠보면, **4~5개일 때 중복률이 가장 높고(약 2.5%)**, 그 이상으로 늘어나면 오히려 낮아지는 **비단조(non-monotonic) 패턴**

즉 "도구를 많이 붙일수록 중복이 는다"는 직관적인 가설은 데이터로 뒷받침되지 않았습니다.

## 중복 여부를 가르는 결정적 요인: 엔티티 ID

분석 과정에서 드러난 흥미로운 지점은, "두 번 호출됐다"는 사실과 "실제로 두 개가 생성됐다"는 사실을 구분하려면 **응답에 엔티티 ID가 포함되는지**가 관건이라는 점입니다.

- 문서 생성 API 대부분은 생성된 문서의 ID를 응답으로 돌려줌 → 중복 생성 여부 판정 가능
- 이메일 발송 같은 도구는 그냥 "성공" 문자열만 반환 → 판정 불가

실제로 판정이 불가능했던 3,197건 중 2,011건이 바로 이런 경우였고, 응답에 ID를 아예 반환하지 않는 도구가 24종이나 됐습니다. MCP 도구를 설계하거나 선택할 때, 상태 변경 작업의 응답에 고유 ID를 포함시키는 것이 운영 관점에서 중요한 이유가 여기 있습니다.

## 실무자들에게 던지는 질문

작성자는 명확한 결론을 내리기보다, 실제로 MCP 기반 에이전트를 운영 중인 분들의 경험을 구하고 있습니다.

1. **MCP 도구(서버)를 몇 개나 붙여서 쓰시나요?** 도구 수와 중복 실행 빈도 사이의 실제 상관관계가 궁금하다는 것
2. **중복 실행을 겪은 적 있다면 어떻게 발견하셨나요?** 에러 로그로는 안 보이니, 고객 신고로 알게 되는 경우가 많은지
3. **쓰시는 도구들이 응답에 엔티티 ID를 돌려주나요?** 이게 사후 검증 가능 여부를 가르는 핵심이기 때문

## 왜 이 논의가 중요한가

LLM 에이전트에 여러 MCP 도구를 붙여 자동화를 구성하는 패턴이 점점 늘어나는 지금, 이런 '조용한 중복 실행' 문제는 프로덕션에서 실제 비용(중복 이메일 발송, 중복 결제, 중복 문서 생성 등)으로 이어질 수 있는 잠재적 리스크입니다. 벤치마크는 정확도 위주로 설계돼 있어 이런 부작용을 거의 포착하지 못한다는 점도 곱씹어볼 만합니다. 여러 도구를 연결한 에이전트를 운영 중이시라면, 상태 변경 작업에 대한 idempotency key 도입이나 응답 ID 기반 사후 검증 로직을 갖추고 있는지 한 번 점검해보시는 것도 좋겠습니다.
